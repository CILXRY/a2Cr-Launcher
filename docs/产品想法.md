# 产品想法

这份文档回答一个问题：**为什么还要做一个启动器**。
它不是接口约定（那在 `contracts/` 里），也不是路线图。它是判断"某个功能该不该做"的依据。

## 一句话定位

**一个为多版本而优化的 Minecraft 启动器。**

现有的启动器都在解决"装得上、跑得起来"；这个项目要解决的是**同一个玩家在多个版本、多个整合包之间来回切换时的摩擦**。

## 三条原始需求

### 1. 只隔离 mod，别的都共享

现有启动器的"版本隔离"基本是二选一：整份游戏目录隔离，或者全部共享。
但真实需求是**按类别决定隔离粒度**：

- 要隔离：`mods`（不同版本/加载器的 mod 会互相打架）
- 要共享：`resourcepacks`、`shaderpacks`、画面与声音设置

典型痛点：在版本 A 里启用了一套材质包，切到版本 B 就得重新加载一遍；或者某次配置被重置后，资源包列表全变成"已禁用"，只能一个一个加回去。

### 2. 沙盒化 / 复制一个版本

一个自己用的整合包，临时要和朋友联机加几个 mod；回到单人存档时又得把这些 mod 关掉。

**注意**：这条需求本质是"切换一组 mod 的启用状态"，不一定需要真的复制几 GB 文件。
复制是满足它的一种昂贵实现，见下面的"profile"。

### 3. mod 跨版本、跨加载器

整合包是 26.2，朋友的服务器是 1.21。要么装 ViaVersion 系列，要么换版本重装 mod。

需要拆成两半承诺：

- **同加载器跨版本**：可以自动化。mod 池里按 `(加载器, 版本)` 解析出对应构建（Modrinth API 支持按 `game_versions` + `loader` 过滤），换不掉的明确报告。
- **跨加载器**（fabric → forge）：现实中大多数整合包做不到，mod 不是同一批东西。只能"尽力而为 + 报告"，**不要许诺成和上面同一件事**。

## 现有启动器的空档

HMCL、PCL2、BakaXL 的版本隔离是"整份隔离或全共享"的二选一，隔离单位是整个游戏目录。
按类别分粒度隔离，目前没有启动器做。

这既是机会也是警告：**空档不代表用户需要，只代表还没人做**。所以第一个能验证它的版本必须尽早跑起来。

## 四层模型

所有需求最后收拢成一个模型，四层各管一件事：

| 层 | 内容 | 判定规则 | 删了会怎样 |
|---|---|---|---|
| `cache` | assets、libraries、logging 配置、版本 jar | 能重新下载，与用户无关 | 只是下次重下 |
| `pool` | mod、资源包、光影、配置、存档 | 用户提供或导入，无法凭空重建 | 真的没了 |
| `instances` | 哪个版本、启用池里哪些东西、私有日志 | 只是引用 + 少量私有状态 | 实例消失，池子不受影响 |
| `profiles` | 一组命名好的"启用清单" | 实例内的覆盖层 | 回到上一个组合 |

命名按**能否重建**来分，不要按"是否共享"来分——`share` 和 `pool` 都叫"共享"会在文档里互相串。

### pool 内部要再分两类

- **可再生**：mod、资源包、光影（有哈希、能重下、能校验）
- **不可再生**：存档、配置（删了就没了）

这两类放一层里，很容易写出"更新整合包时顺手清理池里没用的文件"这种灾难。清理只能删"哈希未变"的托管文件。

### pool 有三种形态，单位不同

| 形态 | 单位 | 例子 |
|---|---|---|
| 文件池 | 文件 | `mods/<name>-<version>.jar`、资源包、光影 |
| 键值池 | 键 | `options.txt` 里的字段 |
| 存档池 | 目录 | 按 MC 版本分桶的存档 |

## 硬链接的规矩

实例里的 `mods/` 是**真目录**，里面的文件硬链接到 `pool`。这样 `mods` 可按实例自定义，而磁盘只存一份。

四条不可让步的约束：

1. **不能跨分区**。池子和实例在同一个根目录下（都在用户目录里），所以这不是问题；跨盘时回退到复制。
2. **只对只读内容用硬链接**。jar、资源包、光影可以；`options.txt`、`config/`、存档、日志都被游戏原地重写，链接过去就是"多个实例一起变"。
3. **池内文件一旦创建就不再修改**。更新 = 新增一个文件 + 重新链接 + GC 旧文件。这条让"原地覆盖"从根上不可能发生，顺带白送原子更新和回滚。
4. **删池子 ≠ 释放空间**。数据在最后一个名字消失前一直占着盘，所以必须有 GC：池里有、但没有任何实例引用 → 进回收站。实例里"清单没有、也不是链接"的文件属于用户，只读不动。

## 配置共享池（`options.txt`）

不同版本的 `options.txt` 有共同部分（画面、声音、FOV、按键），也有版本独有的键。
思路：像 mod 池一样做一个**配置池**，而不是复制整份文件。

关键点：**池里存的不是文件，是键值声明**。因为 `options.txt` 是游戏拥有、退出时整份重写的文件，存一份完整文件等于和游戏抢所有权。

```text
pool/options/base.txt        ← 版本无关的键
pool/options/<version>.txt   ← 版本无关键的覆盖
profiles/<profile>/options   ← 组合级覆盖
```

启动时按 `base → 版本 → profile` 叠加生成实例的那份；退出时把变更按白名单分流回对应层。

三个必须提前定的决定：

- **用白名单，不要用"两边都有的键"**。交集里混着资源包列表、`guiScale`、`lastServer` 这种含义依赖版本或实例的键。
- **永远不共享的键要列出来**：资源包列表（视情况）、`soundDevice`、`fullscreen`、`lastServer`、任何 mod 写入的键。
- **回写要判断"这次真的改过没有"**（启动时记 hash），两个实例同时开需要锁。**只注入不回写**是零风险的降级方案。

## 已经在契约里落定的

这几条曾经是"想法和契约打架"，现在定了，细节在 `contracts/02-目录结构.md`：

1. **共享是持续的，不是克隆那一瞬间。** 实例里的 `mods` / `resourcepacks` / `shaderpacks`
   是真目录，启动时和池子对账：池里有、实例没有就建硬链接；池里没了就断链。
   所以在 A 里加的包，B 下次启动就能看到。
2. **存档按"共享组"共享，不是按版本名分桶。** 共享组 = 同版本原版，或从同一 mod 基础
   克隆的实例。组外的世界一律独占。存档池默认关闭。
3. **存档绝不链接，只做"副本 + 提升"。** 游戏原地写 region / `level.dat` / `session.lock`，
   共享物理文件必然互相污染——"删除连坐"也因此不可能发生。

## 还没定的

- **profile（需求 2）**：一组命名好的 mod 启用清单，还没定进不进 v2.0；
- **mod 跨版本 / 跨加载器（需求 3）**：同加载器跨版本可自动化，跨加载器只能报告；
- **世界的身份**：文件夹名（改名会断）还是启动器发一个 id 文件；
- **并发冲突**：两个实例先后玩同一个世界时，后提交要不要提示。

## 不做的事

- 不做启动器内置的 mod 汉化/机翻。
- 不做跨加载器的"自动迁移"承诺，只做报告。
- 不为了省空间牺牲正确性：宁可复制，不可让两个实例互相污染。

# 发布规范

## 1. 版本号

SemVer：`主.次.修`。

- `0.x` 阶段允许破坏性变更（v2.0 之前的都算探索）；
- 加了功能 → 次版本 +1；只修 bug → 修订号 +1；
- **版本号只有一个来源**：项目文件里的 `<Version>`（或 `Directory.Build.props`）。
  v1 的教训是版本号写在两处（`pyproject.toml` + `__init__.py`），得手动同步，忘一次就不一致。
  v2 不许再出现第二处。

## 2. CHANGELOG

手写 `CHANGELOG.md`，按 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/)：

```markdown
## [2.0.0] - 2026-12-01
### 新增
### 变更
### 修复
```

- 只写**用户能感知的变化**，不写"重构了 xxx"；
- 每条后面可以带 issue 号；
- 不自动生成：v1 用过 release-please，它只会把 commit 标题堆在一起，读起来没有重点。

## 3. tag

| tag | 什么时候打 | 例子 |
|---|---|---|
| `docs-v2-spec` | 契约冻结，可以开始照着写代码 | 本次 |
| `v2-mN` | 里程碑完成（M1–M5） | `v2-m1` |
| `v2.x.y` | 正式发布 | `v2.0.0` |

打 tag 前工作区必须干净、CI 必须绿（见 `git.md` 第 4 节）。

## 4. 构建产物

| 指标 | 上限 | 为什么 |
|---|---|---|
| 单文件体积 | **60 MB** | 直接对标 v1 的 132 MB（其中 33 MB 是误打包的 `pyrefly`） |
| 输出文件数 | **20 个** | v1 有 1900 多个文件，解压慢、杀软扫描慢 |

超出就要在 PR 里解释，或者砍依赖。

## 5. 发布流程

1. 更新版本号（唯一来源）；
2. 更新 `CHANGELOG.md`；
3. 跑 `12-验收与回归.md` 第 5 节的检查清单；
4. 打 `v2.x.y` tag；
5. 构建 Windows 产物，附在 Release 上；
6. Release 说明直接指向 CHANGELOG 对应小节。

## 6. 回滚

- 线上问题是**打包/配置**造成的 → 重新发一个修订版，不回退 tag；
- 问题是**代码逻辑**造成的 → 从 release 分支 cherry-pick 修复，同样发修订版；
- **永远不要**把已经发布的 tag 改指向。

## 7. 暂不做

- 自动更新（差分更新要等单文件发布稳定后再设计）；
- 自动发布流水线（在 M5 之前，手动发版更快也更容易排查）。

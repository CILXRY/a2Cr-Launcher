## 里程碑

每层都能单独跑起来，卡住不影响前面已经交付的东西。**每完成一个打一个 tag**（`v2-m1`…），
不是为了发版，是为了卡住时能退回去。

| 里程碑 | 内容 | 完成时能干什么 |
|---|---|---|
| **M1 能启动** | 下载（续传 / 校验 / 取消）、版本 JSON 合并、规则求值、参数拼装、Java 发现、进程与日志 | 用 **CLI** 真的启动原版，看到游戏日志 |
| **M2 能玩 mod** | `pool` + 对账 + 硬链接、`instance.json` / `manifest.json`、Fabric / Quilt | 建实例、装加载器，mod 只按实例隔离 |
| **M3 能装包** | 整合包导入（`.mrpack` → CurseForge → HMCL/PCL）、Forge / NeoForge | 导入一个真整合包并启动 |
| **M4 能登录** | 微软设备代码流程、令牌续期 | 进正版服 |
| **M5 对齐 v1 的体验** | Avalonia 界面、搜索、存档池、对象库、profile、跨版本 mod | — |

排期上的三个判断：

1. **M1 用 CLI 验收，不要求 GUI**。CLI 写得快、能跑回归、报错清楚；GUI 在 M1 通过后马上做。
2. **Forge / NeoForge 放 M3**。它要调官方安装器、处理各种版本差异，是最容易卡住的地方；
   放在"已经能用 Fabric 启动带 mod 的游戏"之后，卡住也不影响前面的交付。
3. **登录（M4）可以插队**。它只影响启动参数里的 `accessToken` / `uuid`，和其他模块几乎不耦合。

v1 里已经有能跑的 Forge 安装、整合包导入、微软登录实现（`legacy/v1-python/`），
所以 M3 / M4 是**移植**，不是从零设计。

## 写文档的规矩

- 一份文档只管一件事。改某块只动对应的文件。
- 链接用相对路径，不要写绝对路径。
- 新增契约文件：在本表加一行并续编号。
- **改已经审定的文档**：先在 `13-决策记录.md` 写一行为什么。
  完善中的文档不用走这一步，直接改。

# 下载与进度

## 1. 只有一个入口

**不拆"单文件"和"批量"两个 API。** 批量传一个元素就是单文件下载。

```csharp
public sealed record DownloadItem(
    string Url,
    string TargetPath,      // 直接给出最终路径，不区分池子/实例
    string? Sha1,           // null = 不校验
    long Size);             // 0 = 未知

public sealed record DownloadOptions
{
    public int MaxConcurrency { get; init; } = 8;      // 1–16，设置里可调
    public int MaxRetry { get; init; } = 4;
    public long MaxBytesPerSecond { get; init; } = 0;  // 0 = 不限速；全局共享额度
    public string? ProxyUrl { get; init; }             // null = 跟随系统
    public string? MirrorBaseUrl { get; init; }        // null = 直连
}

Task<DownloadReport> DownloadAsync(
    IReadOnlyList<DownloadItem> items,
    DownloadOptions options,
    IProgress<DownloadProgress>? progress,
    CancellationToken ct);
```

`DownloadReport` 至少包含：`AllSucceeded`、`Failed`（路径 + 可读原因）、
`TotalBytes`、`DoneBytes`。调用方根据 `AllSucceeded` 决定要不要抛异常。

> `【待确认】` "下载限速"是自己在读取循环里做，还是接某个现成的库。
> 本文按"自己实现"写，若改用库，第 4 节换成库的配置即可。

## 2. 单文件语义（照 v1，已验证）

| 项 | 值 | 原因 |
|---|---|---|
| 重试次数 | 4 | 偶发网络抖动 |
| 退避 | `min(0.5 * 2^n, 4.0s)` + 0–0.3s 随机抖动 | 避免整批同时重试打垮服务器 / 代理 |
| 分片大小 | 1 MiB | 断点续传粒度，同时是限速的节流点 |
| 超时 | 连接 10s / 读取 60s | 读取超时不能太短，慢速大文件会被误判 |
| 请求头 | `Accept-Encoding: identity` | **必须**。服务器压缩后字节偏移和本地不一致，续传会错位 |
| User-Agent | `a2cr-launcher/<version> (+repo)` | 标识来源 |

**4xx 不重试**（408、429 除外）：文件在服务器上不存在，重试四次只是白等，
还会把"真问题"拖成半分钟才暴露。

校验顺序：**先比大小，再比哈希**。大小不对直接判错，大小对得上再计算 SHA-1。
v1 对每个已存在文件都算哈希，assets 上万个文件时这一项能吃掉几十 GB 的读 I/O。

已有目标文件时：

- 没给哈希 → 跳过（无法校验，不重下）。
- 哈希匹配 → 跳过。
- 哈希不匹配 → 删除重下（不能把坏文件当缓存）。

## 3. 续传

1. `.part` 已存在且**大于**期望大小 → 一定是坏分片，删掉重下。
2. 否则带 `Range: bytes=<已下载>-`。
3. 服务器返回 `416` → 认为已下完，交给哈希校验判断。
4. **只有返回 `206` 才能追加写**；返回 `200` 必须从头覆盖。
5. `.part` 哈希通过 → 原子 rename 成目标文件。
6. 哈希不通过 → 删除 `.part`，计入一次失败重试。

**绝不允许"先删后写"或原地截断**——文件可能在池子里且被实例硬链接着（`04-文件存储.md`）。

## 4. 并发与限速

- 并发：默认 8，可配置 1–16。并发不是越高越好，小带宽下更高并发反而更慢。
- 限速：**全局额度**，所有任务共享（用户想限的是总带宽，不是单个连接）。
  实现用令牌桶，在每个 1 MiB 分片写完后按需等待。
- **限速产生的等待不能算进读超时**。否则限到 100 KB/s 时，一个 20 MB 文件会被误判超时。
  超时只对"等数据的 socket 读"生效，对自己 sleep 的时间不生效。
- 限速会让总耗时变长，这是预期行为；UI 不要显示"下载失败"或"卡住"。

## 5. 进度

两个维度都要，一个都不能少：

```text
已下载：36M / 300 个   |   总计：200M / 1000 个
```

- **总字节** = 清单里各条目 `Size` 之和。清单里 size 未知（0）的条目不进总字节，
  此时 UI 显示 `200M+` 表示是下限。
- **已下载字节** = 已完成文件的 `Size` + 进行中文件的已写字节 + 跳过/续传文件的已存在字节。
  跳过也要计入，否则进度条会从 0 开始但实际已经下了一半。
- 回调时机：每完成一个文件一次；另外每 200 ms 补一次"进行中的字节"，
  否则下载单个大文件时进度条会长时间不动，看起来像卡死。
- 回调频率上限约 4 次/秒，避免刷爆 UI 线程。
- 回调可能来自工作线程，UI 层负责切回主线程。
- **传了回调就不要输出任何控制台进度**（v1 的契约，保留）。

## 6. 取消

- 统一 `CancellationToken`，抛 `OperationCanceledException`。
- **取消不是失败**：不许包成 `DownloadException`，否则界面分不清"用户取消"和"下载失败"。
- 取消时已写好的 `.part` 必须保留，重新执行同样的下载能续上。
- 批量取消后剩余文件不再启动；已开始的在下一个分片边界退出。
- 最外层必须用 `catch (OperationCanceledException) when (ct.IsCancellationRequested)` 单独接住，
  不能落进通用 `catch` 被转成"下载失败"。

## 7. 代理与镜像

### 代理：应用内设置，三态

| 模式 | 行为 |
|---|---|
| 跟随系统 | 默认 |
| 自定义 | 用户填一个代理 URL（`http://`、`https://`、`socks5://`） |
| 不使用 | 直连，忽略系统代理 |

.NET 的 `SocketsHttpHandler` 原生支持 socks5 / socks4a，一个 URL 就能覆盖三种协议，
不需要为 SOCKS 单独引库。

### 镜像：默认直连，失败时提示

- 只替换 URL 的 host 前缀，**路径和文件名保持不变**。
- **哈希来自 Mojang 的官方元数据，不来自镜像**，所以镜像无法投毒，最多给你 404。
  这也是镜像可以放心支持的根本原因。
- 默认直连；超时或连续失败时提示"要不要换镜像"，不默认启用（镜像会挂）。
- 代理与镜像可叠加：走代理访问镜像。

## 8. 失败上报

| 场景 | 处理 |
|---|---|
| 单文件 4 次重试后仍失败 | 记录原因，批量继续 |
| 批量结束仍有失败 | 返回失败明细，调用方决定是否抛 |
| 安装流程中有失败 | 抛 `DownloadException`，提示"重新执行可继续补下"（已下载的会跳过） |
| 版本列表/元数据网络失败 | 回落本地缓存；缓存也没有才报错 |
| 4xx（408/429 除外） | 立即失败，不重试 |

不要静默失败。v1 的"进度条走完但实际缺文件"是最难排查的体验问题。

## 9. 磁盘空间

批量开始前，用 `TotalBytes` 预检查目标盘剩余空间。不够就直接失败并给出具体数字，
而不是下到一半写崩、留下一堆半截文件。

## 10. 不做

- 分片并行（同一文件多连接 Range）：收益小，服务端兼容风险大。
- 断点续传的 ETag / Last-Modified 校验：Mojang 的 CDN 用哈希就够。
- 自动测速选镜像：先做"失败提示"，不做主动探测。

## 11. 测试点

- `.part` 比目标大 → 重下。
- 服务器忽略 Range 返回 200 → 从头写，不追加。
- 服务器返回 416 → 进入哈希校验。
- 取消后 `.part` 保留，下次续传成功。
- 批量里同一路径重复 → 只下载一次。
- 连续失败 12 个 → 中止并给出可读提示（"一个都没成功且连续失败 ≥ 12"）。
- **404 不重试**，立刻失败。
- 大小不符 → 直接判错，不计算哈希。
- 限速下 20 MB 文件不被判读超时。
- 单文件下载时进度仍在走（字节维度）。

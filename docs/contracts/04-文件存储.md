## 1. 唯一写入口

Core 里**除了 `IFileStore` 的实现之外，任何地方都不许直接写游戏目录的数据文件**。

禁止出现：

- `File.Copy(..., overwrite: true)` 写到实例/共享目录
- `File.WriteAllBytes` / `File.WriteAllText` 写游戏文件
- `new FileStream(path, FileMode.Create)` / `FileMode.Truncate` 覆盖已有文件

CI 里加一条 grep 检查（或在 `Directory.Build.props` 里加分析器）即可，成本几乎为零。
这条纪律是 v2.1 能"只改一个实现类"的前提，事后补要审遍全项目。

```csharp
public interface IFileStore
{
    /// 确保 targetPath 存在且内容符合 spec；已存在且哈希正确则跳过。
    Task<AcquireResult> AcquireAsync(
        string targetPath,
        ContentSpec spec,
        FileOrigin origin,
        IProgress<DownloadProgress>? progress,
        CancellationToken ct);

    /// 删除一个被管理的文件（同时更新 manifest）。
    Task ReleaseAsync(string targetPath, CancellationToken ct);
}

public sealed record ContentSpec(string? Url, string? Sha1, long Size)
{
    public static ContentSpec Download(string url, string sha1, long size);
    public static ContentSpec Local(string existingFile);       // 模板、本地包解压
    public static ContentSpec Empty(int size = 0);              // 生成占位文件
}
```

`AcquireResult` 至少包含：`Success / Skipped / Failed`、实际哈希、是否降级为复制。

## 2. 写入纪律（不可协商）

所有写入路径统一为：

```text
写入 <target>.part  →  计算并校验 SHA-1  →  原子 rename 到 <target>
```

**绝对不允许先删后写、也不允许原地截断。**

原因：实例里的文件从第一天起就是**硬链接**（池子模型）。原地覆盖会**穿透链接改写池子里的唯一副本**，所有共享该文件的实例一起损坏，而且没有任何报错。
rename 会替换目录项、断开链接，正好产生我们要的 copy-on-write 语义。

即使某些文件暂时退化为复制，这条也必须遵守——否则要回头审计每一处写入。

## 3. v2.0：`PlainFileStore`

- `AcquireAsync`：目标已存在且哈希匹配 → `Skipped`；否则按第 2 节写入。
  写入位置是**池子**（`pool/mods` 等），随后立刻建硬链接到实例；
  跨卷或链接失败则退化为复制，并在结果里标记降级。
- `ReleaseAsync`：先断开实例里的链接，再由 GC 决定池里的文件去留。
- 维护 `manifest.json`（`origin` 由调用方传入）。
- **不做内容去重**（同名同内容的重复文件在 v2.1 才合并）。

## 4. v2.1：`ObjectFileStore`

### 4.1 布局

对象库分**名字层**和**物理层**：

```text
pool\mods\fabric\1.21.1\sodium-0.6.1.jar                  ← 名字层：稳定、可读、给启动器用
   └─(硬链接)─ pool\objects\<sha1[:2]>\<sha1>             ← 物理层：内容寻址、只读（v2.1 才有）
instances\<folder>\mods\sodium-0.6.1.jar                  ← 硬链接到名字层
```

- **v2.0 只实现名字层**（`pool/mods` 里的文件就是真文件），物理层等于不存在；
- **v2.1 再加物理层**，把同名的重复内容合并成一份。

分两层的好处：实例的清单指向稳定路径（`mods/sodium-0.6.1.jar`），
不会因为哈希变化而让清单全部失效；去重只在池内部发生。
两层的写入纪律完全相同（第 2 节）。

### 4.2 写流程

1. 目标已存在且哈希正确 → 跳过。
2. 对象已存在（`shared/objects/<sha1>` 命中）→ 校验后直接建硬链接。
3. 否则下载/复制到 `<sha1>.part` → 校验 → move 进对象库 → 设只读 → 建硬链接。
4. 硬链接失败（跨卷、文件系统不支持）→ 退化为复制，计入降级统计。

### 4.3 哪些文件进对象库

| 类别 | 进对象库 | 说明 |
|---|---|---|
| `mods/*.jar` | ✅ | 不可变 |
| `resourcepacks/*.zip` `shaderpacks/*.zip` | ✅ | 不可变 |
| 模板里的资源包/光影包 | ✅ | 不可变 |
| `options.txt` | ❌ | 游戏整文件重写，只能字段级同步（v2.2） |
| `servers.dat` `config/**` | ❌ | 可变；只能整文件注入/回写（v2.2） |
| `saves/**` `logs/**` `crash-reports/**` | ❌ | 正确性问题，省这点空间不值 |

**判断标准只有一条：这个文件在实例生命周期内会不会被原地改写。** 会，就不进对象库。

### 4.4 只读

对象库里的文件设置为只读（`FileAttributes.ReadOnly`），硬链接继承该属性。

- 目的：用户在资源管理器里"拖拽覆盖"会被拒绝（access denied），而不是静默截断共享副本。
- 代价：同名的 mod 不能靠拖拽替换，必须通过启动器的"导入/更新"。
- 启动器自己更新时先清属性，写入后恢复。

### 4.5 GC

分两级，判据都是**清单里的引用**，不是文件系统的链接数
（链接数会被备份工具、资源管理器的操作影响，见 `02-目录结构.md` 不变量 5）：

```text
第一级：池里的名字层文件
  没有任何实例的 manifest.json 引用它  →  从池里移除

第二级：物理层对象
  没有任何名字层文件指向它            →  删除对象
```

注意：**用户手动放进实例、不在清单里的文件不参与 GC**，永远保留。

触发时机：删除实例后、启动时后台惰性扫描、用户点"清理存储"。
GC 必须可中断、可重复执行，且不能删除正在被写入的 `.part`。

### 4.6 占用统计

- 逻辑大小：文件大小求和。
- 实际占用：按 `(volume serial, file id)` 去重求和（`GetFileInformationByHandle`）。
- 存储页展示："逻辑 X GB / 实际 Y GB / 去重节省 Z GB"。

### 4.7 已知风险与缓解

| 风险 | 缓解 |
|---|---|
| 用户用外部工具原地覆盖（`copy /y`、某些解压器） | 只读属性拦截；启动时按 manifest 哈希做抽样校验（不要全量，太慢） |
| 两个实例同时运行并分别改写 | 对象库只收不可变文件，天然规避 |
| 根目录在 OneDrive 等同步盘 | 启用对象库时检测路径并警告，硬链接会被同步客户端破坏 |
| 跨卷 | 硬链接失败自动退化为复制并报告 |
| 备份/还原工具破坏链接 | 接受；链接只是优化，断了不影响正确性 |
| 杀软重复扫描 | 接受，不处理 |

## 5. 测试点

- 克隆后修改 A 实例的 mod → B 实例内容和哈希不变。
- 克隆失败（中途异常）→ 不留下 `.tmp-*` 目录。
- 删除唯一引用的实例 → 对象被 GC；删除其中一个克隆 → 对象保留。
- 对象为只读时，`AcquireAsync` 仍能正常替换（先清属性）。
- 跨卷目标 → 降级为复制并返回降级标记。
- 手工往 `mods/` 丢一个 jar → manifest 里记为 `user`，更新整合包时不被删。
